# 账号知识库功能方案

## 1. 目标与边界

### 1.1 要解决的问题

当前账号只能填写短字段、账号策划、爆款研究和素材信息。用户掌握的业务事实，例如菜品配方、食材来源、供应链、房型设施、路线参数、服务流程、可售套餐和品牌故事，无法稳定地作用于后续选题和文案生成。

本功能提供**账号级知识库**：用户上传 Markdown 文档，系统在生成周计划和笔记文案前检索与当前任务最相关的事实片段，并作为受约束的上下文交给控制台后端 AI。

### 1.2 不做的事情

- 不把完整知识库直接塞入每一次 AI 请求。
- 不将知识库放在 OpenClaw 本机。当前选题和正文由控制台后端 AI 生成，检索也必须发生在后端 AI 调用之前。
- 不用知识库替代账号策划、爆款研究、专家规则或素材库：四者职责不同。
- 第一阶段仅支持 `.md` / `text/markdown`，不支持 PDF、Word、网页抓取、图片 OCR 或表格解析。
- 不自动把知识库事实当作绝对真实。用户上传内容是业务侧资料，系统会注明其来源，但发布前仍需人工核验价格、库存、时效、政策、地址、开放状态等动态信息。

### 1.3 与既有数据的分工

| 数据来源 | 主要作用 | 不承担的职责 |
| --- | --- | --- |
| 账号策划案 | 定位、栏目、目标用户、长期方向 | 提供菜品/服务等细节事实 |
| 爆款研究 `referenceAccounts` | 文风、选题与表达规律 | 证明自有业务事实 |
| 专家规则库 | 已验证的写作与图片改进规则 | 业务资料存储 |
| 素材库 | 可用图片/视频、标签与来源 | 完整描述商品和服务 |
| **账号知识库** | 业务事实、背景资料、产品细节、边界 | 决定文风或自动发布 |

## 2. 用户体验

### 2.1 入口与层级

在左侧导航中新增“知识库”，与“爆款研究”“图片方案”“笔记草稿”处于同一级。知识库仅属于当前选中的账号，切换账号后展示对应资料。

页面包含三个区域：

1. **上传资料**：选择或拖入一个 `.md` 文件，填写可选名称和说明，提交后进入解析状态。
2. **知识文档列表**：显示文档名称、说明、字数、片段数、创建时间、状态，以及“查看 / 替换 / 删除”操作。
3. **使用说明与检索记录**：说明知识库会在周计划、三版标题正文、图片方案和视频方案生成时按任务检索，不会全量传入；每一次 AI 结果显示实际引用的文档和片段数量。

首期不提供自由问答聊天入口，避免把“内容生成的事实依据”和“知识问答”混为一个功能。后续若有明确需求，可以复用本期检索接口增加“查询知识库”。

### 2.2 上传限制

- 单文件格式：仅 `.md`，UTF-8 文本。
- 单文件大小：建议 2 MB；服务端硬限制建议 5 MB。
- 单账号文档数：建议 50 份；总解析文本建议 5 MB 或 50 万中文字符，达到上限后要求删除或替换旧文档。
- 空文档、无法 UTF-8 解码、仅图片链接且无有效文本的文档拒绝入库。
- 上传成功不等于可以立即参与生成。状态依次为：`uploading`、`indexing`、`ready`、`failed`。

### 2.3 文档更新与删除

- **替换**：保留同一文档记录与名称，但删除旧片段和索引后重建；重建完成前旧版本继续可检索，避免生成链路空窗。
- **删除**：立即从列表隐藏，并异步清理原文件、片段和索引；删除后的后续生成不得再引用该文档。
- **查看**：显示原 Markdown 和解析后的标题层级、片段数量，但不展示向量等内部实现数据。

## 3. 数据模型

知识库必须存于服务端数据库和对象存储，不应放在客户端 `localStorage`。客户端只保留当前页面状态。

### 3.1 `account_knowledge_documents`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | bigint | 文档主键 |
| `account_id` | bigint | 所属小红书账号 ID |
| `title` | varchar(200) | 用户显示的文档名称 |
| `description` | varchar(500) nullable | 用户填写的资料说明 |
| `original_filename` | varchar(255) | 原始上传文件名 |
| `storage_key` | varchar(500) | Markdown 原文件对象存储路径 |
| `content_sha256` | char(64) | 内容哈希，用于重复上传识别 |
| `content_chars` | int | 解析后的字符数 |
| `chunk_count` | int | 当前有效片段数 |
| `status` | enum | `uploading/indexing/ready/failed/deleting` |
| `error_message` | text nullable | 解析或索引失败原因 |
| `version` | int | 替换后递增的版本号 |
| `created_by` | bigint | 上传用户 ID |
| `created_at` / `updated_at` | datetime | 时间字段 |

索引：`(account_id, status, updated_at)`；同一账号可对 `(account_id, content_sha256)` 建立唯一约束或上传时提示“内容已存在”。

### 3.2 `account_knowledge_chunks`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | bigint | 片段主键 |
| `document_id` | bigint | 归属文档 |
| `account_id` | bigint | 冗余账号 ID，便于按账号检索 |
| `chunk_index` | int | 文档内顺序 |
| `heading_path` | varchar(1000) | Markdown 标题路径，例如 `菜单 > 战斧牛排 > 熟度建议` |
| `content` | text | 用于检索和注入 AI 的文本 |
| `token_count` | int | 切块后的 token 估算值 |
| `embedding` | vector / 外部向量 ID | 语义检索向量或向量库标识 |
| `content_hash` | char(64) | 片段去重和重建校验 |
| `created_at` | datetime | 创建时间 |

索引：`(account_id, document_id, chunk_index)`，以及向量索引。若当前服务端没有向量数据库，可先在 PostgreSQL + pgvector 实现；不建议由客户端计算或保存 embedding。

### 3.3 生成记录中的引用快照

为了可解释和复盘，每个生成结果应保存轻量引用信息，而不是复制完整知识内容：

```json
{
  "knowledgeReferences": [
    {
      "documentId": 31,
      "documentTitle": "云朵西餐厅菜单与食材.md",
      "chunkId": 180,
      "headingPath": "主菜 > 战斧牛排",
      "score": 0.82
    }
  ]
}
```

- 周计划：保存到 `weekly_plan` 的 JSON 扩展字段或独立 `weekly_plan_knowledge_references` 表。
- 单篇文案：保存到 `note_task` 的 JSON 扩展字段或独立 `note_task_knowledge_references` 表。
- 图片/视频方案：同样保存引用快照，以便知道某张信息卡或镜头为什么包含某一业务信息。

引用快照用于审计和页面展示，不作为下一次生成的检索输入。下一次生成必须从当前 `ready` 文档重新检索，避免删除或替换资料后继续使用旧内容。

## 4. 入库与检索方案

### 4.1 Markdown 解析与切块

服务端上传完成后执行异步入库任务：

1. 校验 MIME、扩展名、大小和 UTF-8 编码。
2. 读取 Markdown，去除空白、HTML 注释和无意义重复内容；保留标题、列表、表格文本和链接文案。
3. 按 Markdown 标题层级优先切块；当一个标题段落过长时，再按自然段拆分。
4. 每个片段建议为 **350-700 中文字符**，保留前后 **60-100 字符**重叠；不得跨账号混合切块。
5. 写入片段、计算 embedding、建立向量索引；全部成功后文档状态变为 `ready`。

切块需将 `heading_path` 作为上下文前缀。这样“价格”“原料”等常见词不会脱离所属菜品、房型或服务项目。

### 4.2 检索输入

检索请求由控制台服务端发起，至少包含：

- `accountId`
- `stage`：`weekly_plan`、`draft_variant`、`image_plan`、`video_plan`
- `query`：根据账号定位、完整策划案、已选本周目标、周重点、当前任务的标题/内容目标/核心观点拼接
- `topicTitle`、`contentGoal`、`coreView`（单篇阶段）
- `maxChunks`、`maxCharacters`

不可把用户原始上传 Markdown 从浏览器随生成请求反复上传。

### 4.3 检索策略

采用“关键词召回 + 向量召回 + 重排”的混合检索：

1. 在当前账号所有 `ready` 片段中，使用关键词和向量各取 Top 20。
2. 合并、去重，再用 query 与标题路径做重排。
3. 优先保留与具体产品、地点、服务、对象直接相关的片段；同一文档最多占最终结果的 60%，避免单一大文档垄断。
4. 过滤过短、相互重复、与当前主题无关的片段。
5. 返回引用信息和片段正文。

若服务端暂不具备 reranker，第一期可以用向量相似度 + 标题关键词加权，保留接口字段，后续无须改客户端即可升级。

### 4.4 上下文预算

| 生成阶段 | 检索数上限 | 注入正文上限 | 用途 |
| --- | ---: | ---: | --- |
| 生成一周计划 | 6 个片段 | 4,500 中文字符 | 帮助确定本周具体对象、可写事实和选题方向 |
| 生成三版标题正文 | 4 个片段 | 3,000 中文字符 | 支持当前单篇的细节、表达边界和事实准确性 |
| 图片方案 | 4 个片段 | 2,500 中文字符 | 提供产品外观、空间、流程或不可改变事实 |
| 视频方案 | 4 个片段 | 2,500 中文字符 | 提供镜头内容和不可虚构事实 |

超出预算时按重排分数截断到完整段落，不能从句中截断。知识库文本应始终显著小于策划案、爆款研究和专家规则的总 Prompt 预算。

## 5. 生成流程改造

### 5.1 生成一周计划

当前周计划输入已包含账号、完整策划、爆款文风、本周目标规则、历史主题和周重点。新增步骤：

1. 前端提交现有周计划参数，不提交知识库原文。
2. 服务端根据账号信息、本周目标、周重点和完整策划构造检索 query。
3. 检索最多 6 个知识片段。
4. 将结果作为 `## 当前账号知识库检索结果` 注入 AI Prompt。
5. 要求 AI：优先将可写、相关且非动态的事实转化为具体选题；不得把资料目录、知识库、检索或内部判断写入周计划面向用户的字段。
6. 保存周计划和 `knowledgeReferences`。

若用户在“本周是否有特殊房型/套餐/活动”中主动填写重点，该重点仍优先于检索和历史去重规则；知识库只补充背景，不能覆盖用户主动定义的主题。

### 5.2 生成三版标题正文

当前三版生成读取单篇任务、已选爆款文风、专家规则、运营目标专项限制。新增步骤：

1. 以当前 `topicTitle + contentGoal + coreView + requiredMaterials + 账号信息` 检索最多 4 个片段。
2. 将检索结果传入 `generateDraftVariants` 的 Prompt。
3. 明确指令：
   - 只能将检索结果作为业务事实和细节来源。
   - 不得杜撰检索结果中没有的价格、库存、优惠、产地、认证、功效、活动、路线参数、开放状态或用户评价。
   - 动态信息只能作为“以门店/官方当日信息为准”的内部风险项，不得以知识库文本替代人工确认。
   - 不得写“资料显示”“知识库提到”“根据内部资料”等暴露来源的表达。
   - 文风仍以本篇唯一爆款文风参考为准；知识库不能改变文风职责。
4. 保存每个生成批次所引用的知识片段 ID。

### 5.3 图片和视频方案

图片、视频方案也应先检索，但只允许知识库影响：

- 真实商品特征、固定空间/设备特征、服务流程、不可改变的规格与禁区；
- 信息卡应该表达什么已确认事实；
- 哪些画面/信息必须避免伪造。

不得因知识库中出现菜品名称或路线名称，就假设存在对应的真实图片、视频或授权素材。素材可用性仍由素材库和用户选择决定。

### 5.4 无知识库或检索失败的降级

- 没有 `ready` 文档：按当前流程生成，不报错。
- 检索无相关结果：传入空结果，按当前流程生成；页面可显示“本次未引用知识库”。
- 索引服务异常：不阻断生成，记录 warning 和服务端监控日志；不得把过期缓存或其他账号资料作为替代结果。
- 单篇必须依赖某资料才能成立时，AI 应减少不可证实细节，而不是编造。

## 6. Prompt 注入规范

知识库注入内容必须结构化、可追溯：

```md
## 当前账号知识库检索结果（仅供事实参考）

[K1] 来源：云朵西餐厅菜单与食材.md > 主菜 > 战斧牛排
内容：……

[K2] 来源：云朵西餐厅门店服务.md > 聚餐场景
内容：……

### 使用规则
- 仅使用与本篇主题直接相关且可从上述文本明确得出的事实。
- 不把资料来源、检索过程或内部核验写入面向用户的标题、正文、图片文字或视频口播。
- 价格、日期、优惠、库存、营业时间、开放状态等可能变化的信息，除非本次已人工确认，不得写成确定事实。
- 当知识库、账号策划、用户本周重点发生冲突时，优先级为：用户本周重点 > 已确认专家规则 > 账号策划的风险边界 > 知识库；冲突内容不要自行调和或虚构。
```

知识库不能要求固定正文顺序。它只提供“可以写什么”和“不能擅自扩展什么”的事实边界；周计划与正文的选题角度、信息顺序和文风仍由现有策略与爆款文风机制控制。

## 7. 前端改造

### 7.1 新页面

新增 `knowledge` tab，至少包含：

- 空状态：说明上传 Markdown 后会在后续计划、文案、图片和视频方案中按需参考。
- 上传区：文件选择、文档标题（默认文件名）、资料说明、上传按钮和状态提示。
- 文档表格或列表：名称、说明、大小/字符数、片段数、状态、更新时间、操作。
- 文档详情抽屉：原文预览、标题结构、索引状态、错误信息。

删除前必须二次确认，因为删除会影响之后的检索结果。

### 7.2 已使用知识的展示

在以下结果区域增加紧凑的“本次参考资料”折叠区：

- 本周内容计划；
- 三版标题正文；
- 图片方案；
- 视频方案。

展示文档标题、标题路径和引用数量；默认不展示完整知识片段，避免页面冗长。用户可展开查看实际被注入的文本和“仅供事实参考”说明。

### 7.3 不改变的交互

- 用户不必每次选择要检索哪些文档，默认检索当前账号全部 `ready` 文档。
- 不增加“每次生成全量导入知识库”的开关。
- 不改变草稿箱任务对 OpenClaw 的职责：OpenClaw 接收已经确定的标题、正文、图片/视频路径；不需要读取或检索控制台知识库。

## 8. 服务端接口建议

以下为建议接口形态，实际路径可按现有 `/client` API 规范调整。

### 8.1 文档管理

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `POST` | `/accounts/{accountId}/knowledge-documents/upload` | multipart 上传 `.md`，创建文档和异步索引任务 |
| `GET` | `/accounts/{accountId}/knowledge-documents` | 获取列表与状态 |
| `GET` | `/accounts/{accountId}/knowledge-documents/{documentId}` | 获取详情和原文预览 |
| `PUT` | `/accounts/{accountId}/knowledge-documents/{documentId}` | 更新标题/说明，或替换文件并重建索引 |
| `DELETE` | `/accounts/{accountId}/knowledge-documents/{documentId}` | 删除文档、片段和索引 |

上传成功响应至少返回：`id`、`status`、`title`、`contentChars`、`chunkCount`（索引中可为 0）、`errorMessage`。

### 8.2 内部检索接口

不建议把知识片段检索直接暴露给浏览器。控制台前端调用自己的 Next route，Next route 或后端生成服务再调用内部检索服务：

```ts
retrieveAccountKnowledge({
  accountId,
  stage: "weekly_plan" | "draft_variant" | "image_plan" | "video_plan",
  query,
  topicTitle,
  maxChunks,
  maxCharacters
})
```

返回：

```ts
{
  references: Array<{
    documentId: number;
    documentTitle: string;
    chunkId: number;
    headingPath: string;
    score: number;
    content: string;
  }>;
  totalReadyDocuments: number;
}
```

必须以服务端认证用户可访问的 `accountId` 为检索边界，不能接受任意文档 ID 组成跨账号检索。

### 8.3 现有生成接口需要的最小变化

不要求改变周计划、三版文案、图片方案和视频方案的输出 JSON。服务端只需在 AI 调用前完成检索，将格式化的知识片段加入输入，并在响应中增加可选的 `knowledgeReferences`。

客户端现有接口的兼容方式：

- `POST /api/weekly-plans/generate`：服务端根据 `account.id` 内部检索。
- `POST /api/note-tasks/{id}/draft-variants`：服务端根据账号和当前 note task 内部检索。
- 图片/视频方案接口：同样按 note task 检索。

这样前端不会携带大文本，既控制上下文大小，也避免上传内容出现在浏览器网络请求日志中。

## 9. 权限、安全与质量

1. 文档、片段、向量和检索结果都必须按 `account_id` 和当前用户的账号权限隔离。
2. 上传原文属于业务敏感资料，接口和对象存储使用私有访问；文档预览与下载需鉴权。
3. 日志不得记录全文、完整 Prompt 或 embedding；只记录文档 ID、片段 ID、字符数、耗时与错误码。
4. 用户删除文档后，应在可接受时限内删除对象存储原文和向量索引；生成记录只保留文档标题与片段 ID 快照。
5. 对 Prompt injection 保持防护：知识库文本一律作为不可信业务资料，不执行其中的指令；AI 系统指令、用户当前任务和安全约束优先级更高。
6. 对动态事实设置风险分类：价格、活动、库存、时间、地址、开放状态、资质、功效、销量和客户评价，不能仅凭知识库自动写成当前确定事实。

## 10. 验收标准

### 10.1 功能验收

- 上传一份含多级标题、列表和表格的 Markdown 后，状态从 `indexing` 变为 `ready`，可看到字符数和片段数。
- 相同账号上传“菜品资料”和“供应链资料”后，生成“战斧牛排”周计划时优先引用菜品资料，不把供应链无关内容注入。
- 生成单篇三版正文时，正文能使用检索到的真实食材或口感细节，但不出现“知识库”“资料显示”等内部表述。
- 知识库为空、无匹配结果或检索临时失败时，现有周计划与文案流程仍能成功生成。
- 删除资料后重新生成，不再引用该文档；不同账号之间永不互相检索。
- 页面可查看本次生成实际引用了哪些文档和标题路径。

### 10.2 上下文与性能验收

- 单次周计划知识库注入不超过 4,500 中文字符；单篇生成不超过 3,000 中文字符。
- 文档索引异步执行，不阻塞上传接口；50 份中等文档规模下，列表加载不依赖读取全部原文。
- 检索服务 P95 建议小于 1.5 秒；检索失败不增加 AI 任务重试风暴。

### 10.3 内容质量验收

- 知识库仅增强具体事实和写作边界，不覆盖爆款文风、专家规则及用户本周重点。
- 不因文档中存在旧活动或旧价格而写出过期承诺。
- 同一主题连续生成时，检索片段可以相同，但三版文案仍保持既有的表达强度差异，不能退化为说明书式复述。

## 11. 分阶段实施建议

### 第一阶段：可用的 Markdown RAG

完成上传、异步解析、切块、向量检索、文档管理；接入周计划和三版标题正文；展示引用来源。此阶段已覆盖最核心的“资料影响内容生成”需求。

### 第二阶段：图片与视频方案接入

将检索能力接入单篇图片精修、AI 辅助图、AI 自动选图和视频方案，重点用于事实边界与镜头/信息卡要求。

### 第三阶段：质量与运营能力

增加资料版本对比、检索质量反馈、指定文档优先级、知识库问答、更多格式导入。任何 OCR、网页抓取或文件格式扩展都应独立评估数据质量和版权风险，不应与第一阶段绑定。

## 12. 关键决策

1. 知识库为**账号级、服务端持久化、按需检索**，不是客户端缓存，也不是 OpenClaw 本地目录。
2. Markdown 原文用于管理和预览，切块/向量用于检索；二者都保留。
3. 周计划与单篇文案使用不同 query 和不同预算，不能共享“一次全量检索结果”。
4. 知识库提供事实与边界，爆款研究提供文风，专家规则提供优化约束；三者不可互相替代。
5. 服务端检索失败时应降级生成；资料不足时不应编造。
